## 一、 问题逻辑链：华为痛点 $\rightarrow$ 现有基线缺陷 $\rightarrow$ 老师方案（DRAPER）

### 1. 华为提出的核心工程痛点（采样式反馈优化的“程序信息不一致”）
反馈编译优化（PGO）依赖三类关键运行时信息：**循环运行次数**（指导循环展开/向量化）、**函数运行信息**（指导函数内联）、**分支跳转信息**（指导基本块布局重排）。现有工业界方案面临两难：
*   **插桩式 PGO（Instrumentation）**：在早期未优化 IR 上插桩。计数精确、块一一对应，但运行开销高达数倍，且需额外构建版本，难以在终端生产环境部署。
*   **硬件采样式 PGO（Sampling，如 x86 LBR/PEBS、ARM SPE/BRBE）**：直接采集**优化后的生产二进制**，开销极低。但由于优化后二进制已经历了**函数内联、基本块克隆、尾合并/分支折叠、循环展开**，导致采集到的二进制 BB 样本无法直接一対一映射回编译器消费 Profile 的**早期未优化 IR**（即“采集阶段与使用阶段程序特征不一致 / Profile-Missing”），且硬件稀疏采样自带随机噪声与滑移（skid），映射回早期 IR 后不再满足控制流守恒。

### 2. 现有基线方法（LLVM AutoFDO / profi, POPL'22）的做法与局限
*   **现有做法**：通过调试信息或伪探针（pseudo-probe）把二进制样本映射回早期 IR，再用最小费用流（`profi`）强行修复不守恒的计数，优化目标是**让每个基本块的还原计数尽量接近真实计数**（$\min \|\hat{c} - c_{\text{true}}\|$）。
*   **两大局限**：
    1.  **未将编译变换比例建模进观测方程**：优化后的一个探针可能对应内联后的特定上下文，或互斥分支合并后的总和，简单点估计映射无法解耦多副本分摊与合并关系。
    2.  **“计数误差变小 $\neq$ 编译后性能更好”**：`profi` 原论文已在 SPEC CPU 2017 上发现，部分程序计数还原更准后，运行性能反而倒退 5%。原因是编译器并不直接消费绝对计数，而是消费**带阈值的局部决策谓词**（如：分支概率是否 $>80\%$、内联收益是否大于成本、块间局部先后次序）。当采样噪声落在阈值附近时，即使计数误差很小，也会触发**决策翻转（Decision Flip）**，导致错误内联或劣化布局。

### 3. 老师方案（DRAPER）的解决逻辑
针对上述两个局限，DRAPER 不做黑盒神经网络计数拟合，而是改变问题结构，分四步解决：
1.  **建立编译变换证据图（TEG）**：利用伪探针（`pseudo-probe`）和编译优化记录（`Optimization Remarks`），把早期 IR 与优化后二进制之间的**内联（inline）、克隆（clone）、互斥路径合并（merge）、循环展开（unroll）**显式构建为稀疏观测矩阵的系数，解决“优化前后程序特征不一致”问题。
2.  **流一致反演与不确定性区间估计**：在严格满足**早期 IR 控制流守恒（流入=流出）、函数调用图一致、非负性**的硬约束下，通过稀疏线性规划反演出循环、函数、分支频次；并通过 20 次参数与映射候选重采样，输出每个块/边频次的**置信区间（不确定性范围）**，而非单点估计。
3.  **极低预算的稀疏主动校准（Sparse Calibration）**：参考 CC'24 精确降开销思想，仅针对不可辨识或高风险的决策敏感位置，在每程序最多 3 个锚点、动态计数更新量不超过总计数 $1\%$ 的预算内补充实测锚点，消除关键路径歧义。
4.  **编译器决策风险投影（Decision-Risk Projection）**：对齐 LLVM 后端实际消费 Profile 的四类谓词（分支概率 $>80\%$、基本块热度、内联成本阈值、机器块布局次序），计算每个决策在采样不确定性下的翻转概率与静态代价；在总计数改动量 $\le 1\%$ 且保持流守恒的前提下，对高风险阈值附近的计数做有界修正，并进行编译回放检验。

## 二、 为什么划分“开发集 / 验证集 / 测试集”？（各程序之间是什么关系）

需要明确说明：**SQLite、zstd、FFmpeg 等每个程序都是完全独立的任务，绝对不是把 SQLite 上算出来的 Profile 或优化结果搬到 zstd 上使用。**

*   **单个程序内部的执行逻辑**：
    *   对 `SQLite`：运行 SQLite 采集输入 $\rightarrow$ 提取 SQLite 的变换证据图与采样观测 $\rightarrow$ 在 SQLite 的控制流图上求解恢复出 SQLite 的 Profile $\rightarrow$ 编译生成优化后的 SQLite 二进制 $\rightarrow$ 在 SQLite 的独立测试输入上测速。
    *   对 `zstd` 和 `FFmpeg`：各自独立执行属于它们自己的上述完整编译与推断流程。
*   **跨程序划分开发集/验证集/测试集的真实目的（对应老师方案第 17、19 节 `leave-program-out`）**：
    *   DRAPER 算法本身包含一组**通用算法超参数与启发式规则**（例如：计数有界修改预算设为 `1%`、分支极性阈值设为 `80%`、补充插桩上限设为 `3` 个锚点、置信区间校准扩张倍数设为 `1.0625` 等）。
    *   **开发集（Development，44 项，含 SQLite、Embench、部分 LLVM 多源程序）**：允许我们在研发过程中观察其反例、诊断退化原因，并据此调整上述算法规则与超参数。
    *   **验证集（Validation，12 项）**：用于区间校准与中间规则核对。
    *   **测试集（Test，14 项，含 zstd、FFmpeg、PolyBench 测试子集等）**：**算法代码与超参数冻结后**，将同一套 DRAPER 算法原封不动地运行在这些未参与调参的程序上，检验算法规则是否对不同类型的未知程序同样有效（即检验算法本身的泛化性，而非跨程序迁移 Profile 数据）。

## 三、 实验设置与对比基线

*   **运行硬件与工具链**：
    *   **CPU**：`Intel(R) Xeon(R) Platinum 8358P CPU @ 2.60GHz`（计时绑定在单核 CPU 127 上运行，消除跨核迁移抖动）。
    *   **编译器版本**：`Clang / LLVM 23.1.4`（配合自研 C++ 插件接口 `draper-llvm` 导出 CFG、调用图、伪探针映射与机器块顺序）。
    *   **采样与重采样设置**：固定随机种子 `42`；优化后探针计数按采样率 `1/64` 进行泊松采样产生观测；不确定性估计使用 `20` 次重采样。
    *   **计时方法**：每个程序各编译版本交错运行（Paired Interleaved Rounds）**15 轮**，每轮批次目标时长 `0.3s`，使用 Bootstrap（2000 次抽样）计算几何平均加速比及 95% 置信区间（CI）。输出正确性校验在计时外独立执行。
*   **四个对比编译版本（均测量编译后生成的目标程序运行速度）**：
    1.  **`baseline`**：无 PGO 的标准 `clang -O3` 编译版本。
    2.  **`profi`（核心对标基线）**：POPL'22 *Profile Inference Revisited*，即 LLVM 主线自带的最小费用流恢复算法编译出的版本。
    3.  **`calibrated`（DRAPER 第一阶段）**：使用变换证据图（TEG）流一致恢复 + 最多 3 个锚点的稀疏校准 Profile 编译出的版本。
    4.  **`risk-projected`（DRAPER 第二阶段）**：在 `calibrated` 基础上叠加编译决策风险有界投影（改动预算 $\le 1\%$）及编译回放验收后编译出的版本。
*   **数据集规模（全部套件共 80 项实验任务 / 70 个独立工作负载已 100% 完成算法与有效计时）**：
    1.  **现代大型工业应用（3/3 项完成）**：`sqlite-modern`（311,070 行）、`ffmpeg`（136,356 行）、`zstd`（43,441 行），均使用独立于采集输入的评价输入测速。
    2.  **PolyBench 循环计算内核（27/27 项完成）**：涵盖线性代数、模板计算、动态规划等密集循环。
    3.  **LLVM MultiSource 多源真实程序套件（40/40 项完成）**：涵盖 MiBench、Ptrdist、Prolangs、Trimaran、Mediabench 等多文件应用，同时完成了“早期计数对照（40/40 项）”与“优化后探针观测（40/40 项）”全量对比。
    4.  **Rodinia / MediaBench 子集（10/10 项完成）** + **Embench 嵌入式原型套件（6/6 项完成）**。

### 2. 现代大型工业应用（SQLite / FFmpeg / zstd，优化后探针观测 + 独立测试输入）

在 3 个数万至数十万行代码的真实应用上，同时对比**相对无 PGO 的 `-O3`（`baseline`）提速**与**相对 LLVM `profi` 的表现**：

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **ffmpeg**（测试集 / 13.6万行） | 78,431 | **1.65% $\rightarrow$ 0.18%**（误差降低 89%） | 96.31% / 80.37% | `profi`: +18.93%<br>`calibrated`: **+18.15%** `[+16.65%, +19.31%]`<br>`risk-projected`: **+14.62%** | **-0.66%** `[-1.25%, +0.30%]`（统计持平） | -3.63% `[-4.26%, -2.61%]` |

**结果解读**：
1.  **第一阶段（`calibrated`：TEG 变换观测恢复 + 稀疏校准）大幅降低计数误差并取得显著 PGO 加速**：相比普通 `-O3` 编译，DRAPER 在 `ffmpeg` 上提速 **+18.15%**，在 `sqlite-modern` 上提速 **+11.28%**；在 `ffmpeg` 和 `zstd` 上，基本块计数误差分别从 `1.65%` 降至 **`0.18%`**、从 `69.95%` 降至 **`52.67%`**，且 `calibrated` 二进制的运行速度与 `profi` 统计持平（95% 置信区间均包含 0）。
2.  **定位出第二阶段（`risk-projected`）静态错误代价模型的局限**：在 `ffmpeg` 和 `sqlite-modern` 上，`calibrated` 原本与 `profi` 持平，但叠加 `risk-projected`（以“执行频次 $\times$ 静态指令数”作为决策错误代价 $w$）后，运行时间反而比 `calibrated` 慢了 1.5%~3.0%。这说明**不能仅用静态指令数近似大型程序中内联/布局翻转的真实运行时间代价**。

## 六、 现存问题诊断与下一步计划

1.  **当前核心瓶颈：决策错误代价 $w$ 的静态近似不准**
    *   我们的**第一阶段（`calibrated`：TEG 变换观测恢复 + 流守恒 + 稀疏校准）**已经能大幅降低计数误差（如 FFmpeg 降至 0.18%），并在大型应用上取得与 `profi` 持平、比 `-O3` 快 11%~18% 的运行性能，同时将多源套件中“计数改善却性能下降”的反例减少 67%。
    *   但**第二阶段（`risk-projected`）**目前使用“恢复频次 $\times$ 静态指令数”作为决策翻错代价 $w$，虽然在 PolyBench（+0.151%）和 LLVM 多源优化后观测（+0.071%）上带来正向提升，却在 SQLite（-2.19%）和 FFmpeg（-3.63%）上造成了负向微调。
2.  **下一步具体改进**：
    *   **修正决策代价模型**：对开发集中的退化案例（如 `automotive-bitcount` 循环展开阈值翻转、`SQLite` 内联/布局决策），通过单决策干预对照（固定单个内联或布局决定）测量真实的耗时与代码膨胀敏感度，替代粗糙的“静态指令数”权重。
    *   **过滤无效补充锚点**：在 SQLite 上发现 3 个补充锚点中有一处选在了终止于 `unreachable` 的冷块上（实测计数为 0），下一步在 `select_anchors` 中过滤 `unreachable` 块并按有效信息增益选点。
    *   **接入真实硬件采样与多输入测试**：目前全部 80 项基准实验已 100% 跑完，下一步将已跑通的真实硬件 LBR 采样数据（`perf.data` $\rightarrow$ `llvm-profgen`）及 cBench 多输入接入当前 TEG 恢复管线。
