## 一、本周结论摘要

老师方案的出发点是：**采样 profile 还原的目标不应是"让每个 count 更精确"，而应是"让消费这些 count 的编译器决策保持安全"**（[方案第 11 行](idea和研究背景/（老师的idea）DRAPER-CCF-A算法模型方案.md)）。

本周围绕这一出发点做了三件事：

| 工作 | 状态 | 说明 |
|---|---|---|
| 恢复算法原型 | ✅ 完成 | 流约束恢复 + 风险选点，在公开基准上跑通全流程 |
| **真实硬件采样闭环** | ⭐ **首次打通** | 本机 CPU 自带 LBR，bzip2 上采到 9434 个真实样本 |
| 文献对标 | ✅ 完成 | 发现 profi 论文自证"profile 精度与性能非单调" |

**但要如实说明**：本周真实硬件实验跑的是 **LLVM 自带的 profi 与频次传播**，**不是老师的 DRAPER 算法**。老师算法的真实数据接入是下一步的首要任务。

## 二、选题依据：为什么"盯决策"是对的

### 2.1 老师方案的判断

方案指出，编译器并不直接消费绝对 count，而是消费一组**局部决策谓词**（[方案 §1，第 23–31 行](idea和研究背景/（老师的idea）DRAPER-CCF-A算法模型方案.md)）：

> 1. 这个基本块是否是热点；
> 2. 这条边概率是否超过阈值；
> 3. 这个调用点的内联收益是否超过成本；
> ...

由此得出的结论是（[方案第 33 行](idea和研究背景/（老师的idea）DRAPER-CCF-A算法模型方案.md)）：

> 两个 counts 误差很大的 profile 可能做出完全相同的优化决策；两个 counts 误差很小的 profile 也可能在关键阈值附近翻转内联、布局或分支概率决策。

### 2.2 本周找到的独立佐证 ⭐

对标文献 **profi（POPL 2022，CCF-A，赛题指定文献 1）** 在实验部分自述（[原文 PDF](data/papers/profi-popl2022.pdf)，文本见 [profi-popl2022.txt 第 1184 行](data/papers/profi-popl2022.txt)）：

> "We do not see a consistent benefit from applying advanced inference techniques, and the overall speedup of sampling-based PGO ranges from around 25% (for 605.mcf_s and 623.xalancbmk_s) to a regression of 5% (for 641.leela_s). Our investigation reveals that, despite having a better profile, various compiler optimization passes may produce sub-optimal results, as they are likely designed and over-tuned for the 'imprecise' profile data."

其给出的机理解释是：**编译器各优化 pass 本来就是针对"不精确的 profile"设计与调优的**。

**这段文献有三重价值**：

1. **正面支持老师方案的出发点**——顶会论文承认"profile 更准 ≠ 性能更好"，与方案"还原误差本身不是终点"（[方案第 293 行](idea和研究背景/（老师的idea）DRAPER-CCF-A算法模型方案.md)）判断一致；
2. **可直接用于论文 Motivation**，无需自行论证；
3. **为实验预期提供合理基准**——连 profi 在 SPEC 上都有 −5% 的倒退，我们在小规模数据上出现"收益不显著"属于正常现象，而非失败。

> 相关背景另见 [插桩式反馈编译优化笔记第 7 行](idea和研究背景/插桩式反馈编译优化.md) 关于插桩式 PGO 两阶段闭环的说明，以及 [PAPER_REVIEW.md](PAPER_REVIEW.md) 对 profi 与 Propeller 的系统对照。

### 3.1 已完成内容

| LLVM 桥接 | [draper/llvm_bridge.cpp](draper/llvm_bridge.cpp) | CFG 导出、精确边计数、稀疏插桩、profi 调用、profile 回写 |

### 3.2 合成数据上的结果

在 Embench 2.0rc2 的 6 个程序上（[RESULTS.md](RESULTS.md)），**基本块计数相对 L1 误差**（越小越好）：

| 程序 | LLVM profi | 流约束恢复 | 追加 3 处插桩 |
|---|---:|---:|---:|
| crc32 | 2.600% | 1.821% | 1.762% |
| slre | 4.623% | 2.534% | 1.803% |
| qrduino | 7.002% | 5.196% | 4.735% |
| nettle-aes | 7.830% | 6.375% | 4.496% |
| picojpeg | 6.040% | 4.121% | 3.992% |
| wikisort | 21.228% | 21.307% | 21.084% |

补测 3 处后，6 个程序误差均低于 profi。但 **wikisort 上流约束恢复未优于 profi**，如实记录。

### 3.3 ⚠️ 必须说明的数据性质

> **上述观测并非真实硬件采集，而是由精确计数生成的 Poisson 模拟数据。**

代码中已有明确标注（[draper/model.py](draper/model.py) 第 96–98 行）：

```python
"kind": "synthetic independent Poisson block observations",
"mapping": "identity at saved early IR, no binary mapping assumed",
```

**含义**：这组实验验证的是"**算法在已知噪声模型下是否正确**"，不能用于主张"在真实硬件上有效"。

## 四、工作二：真实硬件采样闭环 ⭐（本周重点）

### 4.1 硬件条件

本机 CPU **自带 LBR**（Last Branch Record，硬件分支记录），无需额外申请机器即可完成真实采样。详见 [REAL_HARDWARE_PGO.md §3](REAL_HARDWARE_PGO.md)。

| 项目 | 配置 |
|---|---|
| CPU | Intel Core Ultra 7 255HX（`/proc/cpuinfo` 含 `arch_lbr` 标志） |
| 采样事件 | `cpu_core/cycles/u`，周期 100000 |
| LBR 深度 | 32 |
| 采样核 | 性能核 CPU 2，nice 10 |
| 工具链 | Clang/LLVM 23.1.4，perf 7.3.1，内核 7.2.11 |

### 4.2 采集流程

```
bzip2 1.0.8 源码
  → -O3 + pseudo-probe 编译
  → perf record 采集 cycles + LBR 分支栈
  → llvm-profgen 结合二进制与 pseudo-probe 生成采样 profile
  → Clang 读取 profile，分别启用 profi / 频次传播
  → 正确性检查 + 交错计时
```

采样命令（[REAL_HARDWARE_PGO.md §3](REAL_HARDWARE_PGO.md)）：

```bash
perf record -e cpu_core/cycles/u -c 100000 -j any,u \
  -o perf.data -- baseline/bzip2 -9 -c inputs/bible.txt
```

### 4.3 采样结果（可核验）

| 指标 | 数值 | 核验方式 |
|---|---:|---|
| 实际采样数 | **9434** | [perf.script](data/real-pgo-bzip2-v1/perf.script) 中 `cpu_core/cycles/u` 记录行数 |
| 原始 perf.data | 7.34 MB | 文件头为 `PERFILE2` 格式 |
| 分支栈最大深度 | 32 | 达 Intel LBR 上限 |
| profile 中函数入口计数合计 | 921,418 | [samples.prof](data/real-pgo-bzip2-v1/samples.prof) |

### 4.4 四个对照版本

| 版本 | 编译方式 |
|---|---|
| baseline | `-O3`，不使用 profile |
| sample-profi | 采样 profile + LLVM profi 流推断 |
| sample-propagation | 采样 profile + 频次传播 |
| instrumented-pgo | 插桩 PGO（精确计数，作参考上界） |

**profile 确实被消费**（非空跑），优化后 IR 中分支权重节点数为：profi **267**、频次传播 **285**、插桩 PGO **388**（见 [summary.json](data/real-pgo-bzip2-v1/summary.json) 的 `profile_metadata`）。

### 4.5 正确性验证

**12 项检查全部通过**（4 个版本 × 3 个输入）：上游 3 组压缩测试向量逐字节一致；3 个真实语料完成压缩、独立解压、自解压校验。

### 4.6 性能结果

加速率按 `T_O3 / T_优化版 − 1` 计算，正值表示变快。9 轮交错计时，每轮随机打乱版本顺序，配对 bootstrap 给出 95% 区间（[REAL_HARDWARE_PGO.md §4](REAL_HARDWARE_PGO.md)）。

**训练输入 bible.txt**

| 版本 | 加速率 | 95% 置信区间 |
|---|---:|---|
| sample-profi | −0.07% | [−4.01, 2.91] |
| sample-propagation | **−6.82%** | [−15.63, −0.54] |
| instrumented-pgo | −0.37% | [−6.40, 3.96] |
| profi vs 频次传播 | +7.25% | [0.80, 18.22] |

**测试输入 world192.txt**（训练时未使用）

| 版本 | 加速率 | 95% 置信区间 |
|---|---:|---|
| sample-profi | +1.30% | [−1.66, 4.70] |
| sample-propagation | +0.47% | [−2.42, 4.06] |
| instrumented-pgo | +1.78% | [0.28, 3.70] |

**测试输入 E.coli**（训练时未使用）

| 版本 | 加速率 | 95% 置信区间 |
|---|---:|---|
| sample-profi | +0.69% | [−0.97, 2.41] |
| sample-propagation | +0.28% | [−0.29, 1.10] |
| instrumented-pgo | +1.05% | [−0.13, 2.35] |

**判读**：收益幅度小，多数区间跨零（统计不显著）。唯一显著的正面结果为 world192 上插桩 PGO **+1.78%**；唯一显著的负面结果为训练输入上频次传播 **慢 6.82%**。

## 五、⚠️ 需要说明的三点局限

> 主动列出，供组会讨论与后续修正。

### 局限 1：编译标志不对称，横向对比不成立

| 组别 | `-fpseudo-probe-for-profiling` / `-fdebug-info-for-profiling` |
|---|---|
| baseline / sample-profi / sample-propagation | **已添加** |
| instrumented / instrumented-pgo | **未添加** |

证据：[commands.json](data/real-pgo-bzip2-v1/commands.json) 中 clang 编译步按标志组合统计为 `(pseudo, debug) = (True, True)` 共 24 条、`(False, False)` 共 16 条；`llvm-readelf` 显示前三者有 `.pseudo_probe` 段而 instrumented-pgo 为 0。

**后果**：二进制大小 356K / 360K / 364K vs **270K**，相差约 30%，直接影响内联与代码生成。

> **因此"采样 PGO vs 插桩 PGO"的跨组对比不成立，目前只应使用"采样组内部（profi vs 频次传播）"的对比。**
> **修正方案**：统一标志（全部添加或全部去除），重跑本实验。

### 局限 2：关键结论由单个异常轮次驱动

频次传播第 2 轮耗时 0.573 秒，其余 8 轮均在 0.36–0.42 秒之间。用原始数据剔除该轮后重算（n=8）：

| 结论 | 原文数据 | 剔除异常轮次后 |
|---|---:|---:|
| profi vs 频次传播 | +7.25% | **+2.63%** [0.17, 5.64] |
| 频次传播 vs baseline | −6.82% [−15.63, −0.54] | **−2.72%** [−6.26, **+0.08**]（跨零） |

**背景**：测量期间系统负载由 5.26 升至 5.98，仅设置 nice 10，未做 CPU 隔离。

> **修正方案**：增加重复轮次、补充异常点敏感性分析、考虑 CPU 隔离。

### 局限 3：采样仅执行一次（n=1）

单次采样无法估计采样过程自身的方差，而这正是真实硬件实验相对模拟实验的核心价值所在。

> **修正方案**：同一输入重复采样 5–10 次，分别报告。

## 六、⚠️ 本轮的关键定位

> **本次真实硬件实验使用的流推断算法是 LLVM 自带的 profi 与频次传播，不是 DRAPER 的流约束恢复算法。**

对应代码位置为 [run_real_pgo.py](run_real_pgo.py) 第 125–126 行：

```python
for name, enabled in (("sample-profi", "true"), ("sample-propagation", "false"))
```

文档亦已注明："本次性能表中的恢复算法是 LLVM 自带的 profi 与频次传播。DRAPER 接入真实 LBR 数据是下一步。"（[REAL_HARDWARE_PGO.md §1](REAL_HARDWARE_PGO.md)）

**本轮实际完成的是**：打通"真实采样 → llvm-profgen → 编译器"这条基础设施管线，并验证其可用。
**尚未完成的是**：老师算法在真实数据上的验证。当前缺少"真实采样 → 算法输入格式"的转换环节。

## 七、文献对标：评估规模

本周对 5 篇同领域论文的实验规模做了梳理（原文见 [data/papers/](data/papers/)）：

| 论文 | 评估对象 | 规模 | 性质 |
|---|---|---|---|
| **profi**（POPL'22） | 15 个 SPEC CPU 2017 + Clang/GCC + HHVM/Cinder/MySQL | HHVM 热代码 21 MB | 工业级 |
| **Propeller**（ASPLOS'23） | Google 生产应用 Spanner/Search/Bigtable/Superroot | 最大 598 MB、3000 万基本块 | 工业级 |
| **BOLT**（CGO'19） | 5 个 Facebook 生产二进制（**不含 SPEC**） | HHVM 148 MB | 工业级 |
| **Hydra**（OOPSLA'26） | cBench 17 程序 × **20 组输入** | 168 个函数 | 学术（**不测加速比**） |
| **Nisse**（CC'24） | Jotai 950 + LLVM test-suite 134 | 均为小函数 | 学术（**不测加速比**） |
| **本项目当前** | Embench 19（嵌入式）+ BenchmarkGame 7 + bzip2 1 | 最大不足 1 MB | 规模显著偏低 |

**判断**：本项目当前数据规模处于 Hydra/Nisse 一档，但尚未具备它们的两项前提——**每程序多组输入**与**以决策质量替代加速比作为主指标**。

相关原文与对照见 [PAPER_REVIEW.md](PAPER_REVIEW.md) 及 [data/papers/](data/papers/)。
